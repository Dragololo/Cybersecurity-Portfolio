#### First Attempt: A Plain UNION

```shell
MariaDB [employees]> SELECT * FROM employees UNION SELECT * FROM departments; 

ERROR 1222 (21000): The used SELECT statements have a different number of columns
```

**Breakdown:**

- `SELECT * FROM employees` returns every column of every record in `employees`
- `UNION` attempts to combine the two statements into one result set
- `SELECT * FROM departments` returns every column of every record in `departments`
- `;` terminates the query

This was a dead end: `UNION` requires both `SELECT` statements to return the same number of columns, and this error shows the two tables don't match on that count.

**Breakdown:**

- `SELECT * FROM employees` is the original query, returning all six columns of every record
- `UNION` combines it with the second statement
- `SELECT *, 3, 4, 5, 6 FROM departments` reads both real columns from `departments` (`dept_no`, `dept_name`) and pads the remaining four required columns with the junk numbers `3`, `4`, `5`, and `6`
- `;` terminates the query
- `—REDACTED— rows in set` is the total row count, combining both tables

The real `departments` data landed in the first two columns (`dept_no` as `emp_no`, `dept_name` as `birth_date`), and the junk numbers filled the remaining four. `employees` contributed its rows and `departments` contributed one row per department, and the combined total is the row count shown.

The data types did not need to match for this to work. `dept_no` (a `char(4)`) and `dept_name` (a `varchar(40)`) both went into columns typed as `int(11)` and `date` in `employees` without error, and the junk numbers `3` through `6` likewise filled a mix of string (`varchar`), `enum`, and `date` columns without error. This matches MySQL's implicit type conversion for compatible values: numbers convert cleanly into most column types, which is why plain numbers work as junk data even across type boundaries that look mismatched on paper.
